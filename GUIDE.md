# GarminCoach Guide

GarminCoach is an installable, privacy-safe local running-coaching workspace.
This guide is the supported reference for setup, data ownership, plan format,
Garmin workout rendering, and release verification.

## 1. Create a local workspace

```bash
npx create-garmin-coach my-coach
cd my-coach
python -m pip install -r requirements.txt
```

The scaffold accepts an empty destination only. It copies a public whitelist
and creates local, Git-ignored working files; it does not contact Garmin,
publish to npm, connect to Obsidian, or collect voice feedback. Node is
required only for scaffolding. Normal runtime use is Python-based.

Install `requirements-feedback.txt` only if you later opt into local voice
feedback; it intentionally stays separate from the normal runtime environment.

### Repository and generated workspace

The repository and npm package contain only generic code, blank templates,
fictional examples, skills, and tests. The scaffold creates the separate local
workspace where athlete-specific configuration, facts, journal entries, tokens,
feedback, previews, and manifests live. Keep that workspace private; its state
is intentionally ignored by Git.

## 2. Start guided setup

Ask a supported coaching agent to begin. `running-coach` first runs:

```bash
python setup_status.py --json
```

It guides one missing non-secret decision at a time, shows the local files it
proposes to write, and waits for confirmation before writing them. Enter Garmin
credentials directly in `.env`; no skill prints, copies, or asks an agent to
echo credentials or tokens.

## 3. Readiness and local data

| Requirement | Location | Required for |
| --- | --- | --- |
| Garmin credentials and local paths | `.env` | Sync, not guided setup |
| Zones, records, calendar, classifiers, weather fallback | `athlete_config.py` | Data-driven sync |
| Profile and coaching references | `coaching/` | Normal coaching |
| Journal root | `coaching/journal/` by default | Normal coaching |
| Active training plan | `coaching/training-plan.md` | Only plan/render operations |
| Obsidian journal root | `JOURNAL_PATH` in `.env` | Optional |
| Voice feedback configuration | `.env` and local feedback files | Optional |

An explicit no-active-plan state is valid. It prevents plan rendering, not
historical review or onboarding. A sync or optional-feedback failure is
reported with a freshness caveat; it does not erase usable local history.

The scaffold creates these local files and folders:

```text
.env                         # credentials and non-secret local paths
athlete_config.py            # machine-readable data-processing configuration
coaching/
|- athlete-profile.md        # stable profile and Coach Model
|- coach-log.md              # material coaching decisions
|- training-plan.md          # confirmed plan + exactly one PLAN-DATA block
|- training-history.md       # generated by sync.py
`- journal/                  # mandatory per-session and weekly records
```

They, along with data files, Garmin tokens, feedback, and workout manifests,
remain local and ignored by Git. Only blank templates and fictional examples
are tracked. Do not put a credential, token, real activity history, or a local
personal path in a template, example, skill, commit, or npm package.
Ignore rules are rooted at the workspace, so public templates and examples
remain visible and versionable.

## 4. Runtime modules and coaching flow

- `garmin_coach.paths` resolves local workspace paths without machine-specific
  defaults, including an optional local `JOURNAL_PATH` such as an Obsidian
  folder.
- `garmin_coach.readiness` powers `setup_status.py` and reports secret-free
  named readiness requirements.
- `garmin_coach.plan` validates the confirmed plan source:
  `coaching/training-plan.md` and its exactly-one JSON `plan-data` block.
- `sync.py` keeps Garmin facts and generated history in local `data/` and
  `coaching/training-history.md`. A missing or invalid plan only skips plan
  compliance; it does not block retrospective analysis.
- `garmin_workouts.py` renders plan sessions, previews a minimum 14-day
  horizon, and applies only a confirmed manifest-owned preview.
- `skills/` routes coaching through session/race review, mandatory journal
  sync, pattern review, plan work, and explicit Garmin workout requests.

Once sync readiness is complete, `running-coach` runs `sync.py` before
data-dependent advice. Sync writes Garmin facts and generated history; skills
add narrative and coaching decisions to the journal rather than duplicating
raw CSV data. New non-race sessions go through session review, mandatory
journal sync, and pattern review. A load or safety change can then enter plan
adaptation; race confirmation follows the specialised post-race workflow.

Every analysis skill reads the relevant journal evidence. A session or race
review always leaves a coach reading in the journal, even with no voice note
or athlete narrative.

### Optional integrations

An Obsidian folder can be configured as the journal root. It stores the same
mandatory journal; it is not a second source of truth or a prerequisite for
coaching. Generated training history stays outside the vault because it changes
at every sync.

Voice feedback can provide subjective context but is never required. Its
collection/transcription configuration and files remain local and optional.
The journal records a safe association only after ambiguous feedback is
resolved with the athlete.

## 5. Confirmed plans and Garmin workouts

`coaching/training-plan.md` combines human-readable rationale with exactly one
JSON code block tagged `plan-data`. It is the single source for plan compliance
and Garmin workout definitions.

```plan-data
{
  "version": 1,
  "plan": {"id": "example-plan", "status": "active"},
  "sessions": [
    {
      "id": "2026-04-08-intervals",
      "date": "2026-04-08",
      "name": "Intervals",
      "steps": [
        {"kind": "warmup", "distance_m": 1600},
        {"kind": "repeat", "count": 4, "steps": [
          {"kind": "interval", "distance_m": 800, "target": {"kind": "pace", "min": "4:45/km", "max": "5:00/km"}},
          {"kind": "recovery", "time_s": 90}
        ]},
        {"kind": "cooldown", "distance_m": 1600}
      ]
    }
  ]
}
```

Supported step kinds are `warmup`, `cooldown`, `interval`, `recovery`, and
`repeat`. Non-repeat steps have exactly one of `distance_m` or `time_s` and can
declare pace or heart-rate ranges. A valid no-active-plan state uses
`"status": "none"` and an empty session list.

After athlete approval, preview the next at-least-14-day horizon:

```bash
python garmin_workouts.py preview --days 14
# Inspect the saved preview and obtain explicit athlete confirmation.
python garmin_workouts.py --days 14 --apply <preview-id>
```

The preview contains only `create`, `update`, `reschedule`, `unchanged`, and
`unschedule` actions. `--apply` requires the exact saved preview ID and checks
manifest ownership plus remote name/state immediately before a write. Manually
managed Garmin workouts remain outside the system.

## 6. Install coaching skills

Install the folders under `skills/` with your agent's normal skill mechanism;
preserve each folder and its `SKILL.md`. Start with `running-coach`, which
checks readiness and routes to specialised skills. The public package has no
monolithic coaching skill.

The fictional files under `examples/coaching/` show the full handoff from
session evidence to journal, pattern review, coach log, confirmed plan, and
workout rendering.

## 7. Verification and troubleshooting

Run Python behavior tests, Node scaffold tests, and the public-release audit:

```bash
python -m unittest discover -s tests -v
npm test
python release_audit.py
```

The Node test suite packs the package, checks its published file list, installs
that tarball locally, and runs the installed scaffold. The audit scans tracked
public files and npm package contents for credentials, local user paths,
athlete-specific state, legacy workflow files, and excluded working notes.
Publishing remains a separate explicit maintainer action.

- **Readiness is incomplete:** follow the named remediation from
  `setup_status.py`; do not attempt a partial sync using template values.
- **Plan is absent or invalid:** retrospective coaching remains available. Fix
  or approve the plan before previewing workouts.
- **Preview refuses an operation:** resolve the manifest/name/date/remote-state
  mismatch; do not override manually managed workouts.
- **Sync or feedback failed:** continue only with an explicit data-freshness
  caveat. Fix credentials or the optional integration locally; never paste
  secrets into a chat.
